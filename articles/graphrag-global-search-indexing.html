GraphRAG Indexing for Global Search: Architecture, Leiden Communities, and Map-Reduce Synthesis

How GraphRAG solves corpus-wide thematic queries that break standard vector search — through hierarchical Leiden community clustering, pre-computed summary reports, and Map-Reduce execution.

Anshu Kumar

Applied AI Lead · Search & Agentic Systems

October 31, 2026 14 min read
Executive Summary

Global Search is engineered for dataset-wide, thematic, and corpus-level synthesis questions (e.g., "What are the top 5 product quality issues across our entire catalog?" or "What overarching trends emerge from 100,000 customer return tickets?"). While Local Search traverses fine-grained subgraphs around specific seed entities, Global Search never scans raw text chunks at query time. Instead, an offline indexing pipeline organizes the knowledge graph into hierarchical communities using the Leiden algorithm, pre-computes structured Community Reports, and executes a distributed Map-Reduce workflow at query time.

1. The "Why": Why Traditional Vector RAG Fails on Global Questions

Standard vector retrieval architectures split documents into fixed chunks, generate dense vector embeddings, and retrieve the top-$k$ most similar passages via cosine similarity. While effective for narrow fact retrieval, this approach fundamentally breaks down when faced with broad, corpus-wide synthesis queries.

Vector RAG Limitation What Happens on Global Queries Enterprise / E-Commerce Consequence
1. Query-Vector Mismatch Vector search relies on cosine similarity between the query and chunk embeddings. A broad query like "What are common quality defects?" has no single semantic vector matching every defect. Retrieves only chunks containing the literal phrase "quality defects", missing 99% of actual complaints about soles peeling, batteries draining, or blender motors smoking.
2. Context Window Collapse A catalog with 50,000 reviews spans ~15,000,000 tokens. Passing all chunks directly into an LLM context window is mathematically and economically infeasible. Top-$k$ vector retrieval arbitrarily samples 20–50 chunks. An issue affecting 40% of returns might be completely omitted simply because it wasn't in the top-20 nearest vectors.
3. Information Fragmentation Unstructured text chunks are completely isolated. Vector search cannot synthesize patterns that connect across documents. 400 reviews complaining about "sole coming off" and 200 reviews noting "heel stitching snapped in rain" remain separate data points rather than a cohesive "Footwear Moisture & Adhesive Durability" theme.

2. The Solution: The Hierarchical Summary Pyramid

Rather than searching over raw chunks at query time, GraphRAG uses offline indexing to turn unstructured text into an interconnected Knowledge Graph, partitions that graph into modular communities using the Leiden algorithm, and pre-computes Community Reports at multiple levels of abstraction. 

       ▲                Level 0: Corpus Executive Summary (1–3 reports)
      / \               "Overall catalog quality: Footwear adhesives & Electronics thermals"
     /   \              
    /     \             Level 1: Category / Department Reports (10–20 reports)
   /       \            "Footwear Durability", "Mobile Device Power", "Small Appliances"
  /         \           
 /           \          Level 2: Component & Sub-Topic Reports (50–200 reports)
/_____________\         "Sneaker Outsole Glues", "USB-C Fast Charging Heat", "Blender Motors"
 [ Raw Data ]           50,000+ Raw Reviews / Text Units (Never directly scanned at query time!)

At search time, Global Search executes Map-Reduce over these pre-computed reports. This enables an LLM to answer corpus-wide questions with full dataset coverage in seconds for a fraction of the token cost.

4. Step-by-Step Breakdown of Global Search Indexing

Step 1: Document Chunking text_units.parquet

The document ingestion pipeline processes thousands of unstructured customer reviews, return logs, and support tickets, slicing them into standardized TextUnits (typically 1,200 tokens with a 100-token sliding window overlap). 

TextUnit #TU_0142:
"Customer Return #9821: Returned AirFlex Marathon Runner. Sole began peeling away
from the toe box after 14 days of wet-weather running. Customer states adhesive
melted or detached under rain. Refund requested."
Step 2: Entity & Relationship Extraction LLM Extraction

An LLM scans each text chunk with structured prompts to extract domain entities (products, components, defect types, materials) and directed relationships. This converts unstructured prose into discrete nodes and links, turning disconnected reviews into a unified semantic graph. 

• (AirFlex Sneaker) ──[HAS_DEFECT]──> (Sole Delamination)
• (Sole Delamination) ──[CAUSED_BY]──> (Adhesive Breakdown in Moisture)
• (iPhone 15 Pro) ──[HAS_DEFECT]──> (Battery Thermal Throttling)
• (ChefPro Blender) ──[HAS_DEFECT]──> (Motor Overheating)
Step 3: Graph Consolidation & Centrality relationships.parquet

The pipeline resolves entity duplicates across the entire corpus (e.g., merging "iPhone 15 Pro", "iPhone 15Pro", and "15 Pro" into a single canonical entity) and computes co-occurrence weights. Edge weights reflect how frequently two concepts co-occur across thousands of customer experiences.

Step 4: Hierarchical Leiden Community Detection communities.parquet

This is the mathematical core of the Global Search index. The Leiden algorithm partitions the graph into recursive modular clusters:

  • Unsupervised Discovery: Unlike K-Means, you do not need to specify cluster counts in advance. Leiden maximizes graph modularity, uncovering natural topic boundaries.
  • Guaranteed Well-Connected Clusters: Overcomes limitations of older community detection algorithms (like Louvain) by preventing disconnected sub-clusters.
  • Recursive Multi-Resolution Hierarchy:
    • Level 0 (Broadest): 2–4 macro super-communities (e.g., Apparel, Consumer Electronics, Small Appliances).
    • Level 1 (Intermediate): 10–25 category communities (e.g., Footwear Durability, Mobile Power, Kitchen Appliances).
    • Level 2 (Granular): 50–200 component-level topics (e.g., Sneaker Outsole Glues, Fast Charging Heat, Motor Fuses).
Step 5: Generating Community Reports community_reports.parquet

For every detected community at every hierarchy level, an offline LLM acts as a domain analyst, synthesizing connected claims, member entities, and source text into a structured Community Report with pre-computed importance and severity ratings. 

{
  "community_id": 42,
  "level": 1,
  "title": "Footwear Outsole Delamination & Moisture Degradation",
  "summary": "This community encompasses 1,420 customer reviews concerning premature adhesive failure in athletic footwear under wet conditions.",
  "rating": 9.2,
  "findings": [
    {
      "explanation": "Outsoles detached from the toe box within 14–30 days of purchase due to water-soluble polyurethane adhesive failure.",
      "severity": 9.5,
      "impact": "Responsible for 38% of all footwear return requests in Q3."
    },
    {
      "explanation": "Heel counter stitching unravels following exposure to rain.",
      "severity": 7.0,
      "impact": "Affects 12% of high-mileage trail runners."
    }
  ]
}

Why Community Reports are the Secret Sauce: At query time, Global Search never reads the 50,000 raw reviews. Reading 20 Level-1 reports takes ~15,000 tokens versus ~15,000,000 tokens for raw reviews — a $1,000\times$ token compression and execution speedup.

5. Local Search Indexing vs. Global Search Indexing

Notice how differently the two search paradigms utilize the artifacts generated by the indexing pipeline:

Index Component Needed for Local Search? Needed for Global Search? Reason for Difference
Text Units (text_units.parquet) Yes (50% context) ❌ No Local Search quotes exact customer sentences; Global Search requires pre-aggregated summaries.
Entity Embeddings (LanceDB) Yes (Seed matching) ❌ No Global Search has no single entity to search for; it queries across categories.
Graph Triples (relationships.parquet) Yes (1–2 hops) ❌ No Local Search walks specific graph paths; Global Search uses the graph strictly during indexing for community clustering.
Covariates / Claims (covariates.parquet) Yes (Fine-grained facts) ❌ No Claims provide granular proof for local queries.
Community Reports (community_reports.parquet) Partial (25% context) Yes (100% of search) The entire Global Search Map-Reduce engine runs exclusively on community reports.

6. Query-Time Execution: From Index to Answer

When a user asks a high-level question across an enterprise catalog, the engine executes a distributed Map-Reduce workflow over pre-computed reports:

Broad Thematic Query

"What are the top 3 product defect themes across our entire catalog, and what financial impact do they have?"

  1. Level Selection: The engine selects Level 1 category reports (~18 reports spanning Footwear, Mobile, Appliances, Apparel, Home).
  2. Parallel MAP Phase: The 18 reports are split into 3 parallel batches (~6 reports per batch). Parallel LLM "Analyst" workers extract candidate findings scored $0\text{--}100$:
    • Batch 1: Footwear Outsole Delamination (Score: 95, 38% returns)
    • Batch 2: Smartphone Battery Thermal Shutdown (Score: 91, 22% returns)
    • Batch 3: Blender Motor Overheat under load (Score: 84, 15% returns)
  3. Rank & Filter: Candidate points are sorted by severity score descending, filtering out low-confidence noise.
  4. REDUCE Phase: A final synthesis LLM consolidates top-ranked points into an executive briefing citing specific community reports: 
    "Across our catalog of 50,000 products and reviews, the top 3 defect themes are:
1. Footwear Outsole Delamination: Adhesive failure in moisture drives 38% of shoe returns ($420k refund impact).
2. Mobile Battery Thermal Throttling: Rapid 5G discharge and heat causes 22% of electronics exchanges.
3. Small Appliance Motor Burnout: Inadequate thermal fuses in blenders lead to 15% warranty claims.
[Sources: Community Reports #12, #34, #58]"

7. Architectural & Engineering Trade-Offs

Deploying GraphRAG Global Search in enterprise production introduces key engineering trade-offs:

1. Heavy Offline Precomputation vs. Instant Query Execution

Trade-off: Generating community reports across multiple hierarchical levels incurs significant upfront LLM token cost during indexing. However, this shifts computation from query time (where Map-Reduce over raw chunks would timeout or cost hundreds of dollars per query) to offline ingestion, enabling sub-minute executive synthesis.

2. Hierarchy Level Selection vs. Information Resolution

Trade-off: Querying Level 0 provides broad bird's-eye summaries but glosses over subtle product defects. Querying Level 2 catches granular part numbers but increases the number of parallel MAP calls and token consumption. Setting dynamic level selection based on query breadth is essential in production.

3. Incremental Ingestion vs. Community Partition Drift

Trade-off: When thousands of new reviews arrive daily, re-running Leiden clustering across the entire corpus is computationally wasteful. Modern production pipelines employ micro-batch community assignment (assigning new nodes to existing clusters) with scheduled full-graph Leiden re-partitioning periodically.

4. Summarization Bias vs. Grounded Representation

Trade-off: Relying on intermediate community summaries risks propagating subtle LLM hallucinations into downstream search results. Mitigate this by enforcing deterministic JSON schema validation, numeric constraint checks, and strict source chunk attribution within each community report.

Key Engineering Takeaways

  • Community Reports Are the First-Class Index Asset: Unlike traditional RAG where embeddings of raw text chunks rule, Global Search operates 100% on pre-computed hierarchical community summaries.
  • The Leiden Algorithm Solves the "Unknown Unknowns" Problem: Unsupervised modularity clustering automatically groups correlated issues without requiring predefined taxonomy or manual ontology maintenance.
  • Map-Reduce Achieves $1,000\times$ Token Compression: Pre-aggregated community reports compress millions of corpus tokens into a concise set of structured findings that fit comfortably into standard LLM prompts.
  • Severity Scores Enable Algorithmic Pruning: Pre-computed numeric ratings allow the Map-Reduce pipeline to sort, filter, and prioritize critical findings deterministically before final generation.
  • Dual-Engine Synergy: Local Search handles precision entity queries ("Does Battery A work with Phone B?"), while Global Search handles corpus-wide sensemaking ("What are the top failure modes across all electronics?"). A robust enterprise architecture requires both.
